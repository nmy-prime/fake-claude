## 二、完成内容

### 1. 接入 DeepSeek 大模型

在 `pom.xml` 中引入 Spring AI 的 DeepSeek Starter，并用 BOM 统一管理版本，避免各模块版本漂移：

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-deepseek</artifactId>
</dependency>
```

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>${spring-ai.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

API Key 走环境变量注入，不写死在代码和配置文件里：

```properties
spring.ai.deepseek.api-key=${DEEPSEEK_API_KEY}
spring.ai.deepseek.chat.options.model=deepseek-chat
spring.ai.deepseek.chat.options.temperature=0.7
```

启动时只需注入 `DeepSeekChatModel`，由 Starter 自动装配，无需手写 HTTP 客户端。

### 2. 用 ChatClient 封装调用 + 流式输出

用 `ChatClient.builder(...)` 构建客户端，把默认 Advisor 挂在 builder 上，这样每次 prompt 不用重复配置：

```java
ChatClient chatClient = ChatClient.builder(deepSeekChatModel)
        .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
        .build();
```

调用侧用 `stream().content()` 拿到 `Flux<String>`，边收边打印，实现打字机效果；单轮包 try-catch，模型报错不会把整个 REPL 打断：

```java
Flux<String> content = chatClient.prompt()
        .user(message)
        .advisors(a -> a.param(CONVERSATION_ID, "nmy"))
        .stream().content();

content.doOnNext(System.out::print).blockLast();
```

同时做了一个极简的 CLI 交互循环（`Scanner` + `exit` 退出 + 空行跳过），方便本地直接对话调试，不用先写 Controller 和前端。

### 3. 对话记忆

记忆这块分两层：

- **存哪里**：`ChatMemoryRepository` 负责持久化消息，由 Spring AI 自动装配，当前用内存实现，重启即清空。
- **怎么用**：`MessageChatMemoryAdvisor` 在每次请求前后自动做两件事——请求前把历史消息塞进 Prompt，响应后把本轮 user/assistant 消息写回仓库。业务代码完全不用手动拼历史。

关键点是 **conversationId**。Advisor 靠它做会话隔离，不传就没有记忆效果（每次都是新会话），所以每轮都显式带上：

```java
.advisors(a -> a.param(CONVERSATION_ID, "nmy"))
```

目前固定为 `"nmy"` 单会话，后续接入多用户/多会话时改成从请求上下文取即可。

### 4. 记忆压缩

新增 `ChatMemoryConfiguration` 统一管理记忆策略，用 `MessageWindowChatMemory` 的滑动窗口控制上下文规模：

```java
@Bean
ChatMemory chatMemory(ChatMemoryRepository repository) {
    return MessageWindowChatMemory.builder()
            .maxMessages(40)
            .chatMemoryRepository(repository)
            .build();
}
```

策略说明：超过 40 条消息后，从最早的消息开始淘汰，只保留最近一个窗口。这样每轮送入模型的 token 量有上限，长对话不会越跑越贵、也不会顶爆上下文窗口。

> 待办：当前是"硬截断"，被淘汰的历史直接丢失。下一步计划改成"摘要压缩"——窗口满时先让模型把早期对话压成一段摘要，摘要 + 最近消息一起作为上下文，既能控长度又不丢关键信息。

## 三、实现要点 / 易错点

| 易错点 | 说明 |
| --- | --- |
| 忘记传 `conversationId` | Advisor 不报错，但记忆静默失效，表现为"模型失忆"，排查成本高 |
| 记忆仓库没配 | 只声明 `ChatMemory` 不注入 `ChatMemoryRepository` 会启动失败，需确认自动装配生效 |
| `maxMessages` 设太小 | 窗口内塞不下"系统提示 + 本轮问题"，会挤掉关键上下文，40 条是当前折中值 |
| 流式输出不 `blockLast()` | 订阅不触发，控制台什么都不打印，只有主线程退出时才反应过来 |
| Key 硬编码 | 用 `${DEEPSEEK_API_KEY}` 占位，配合 .gitignore，避免密钥进版本库 |
